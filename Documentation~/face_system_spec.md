# Face System Specification

## Architecture

The Face System is a data-driven, atlas-based facial animation framework.
Runtime lookups use stable internal keys generated by the Editor. Designers
name tracks, sprites, and frames, then select them through Inspector controls.

```text
FaceSpriteLibrary
        |
FaceState
        |
FaceAnimation
        |
FaceController
        |
Track Binding
        |
Renderer + Material Index
```

The runtime must not assume that tracks such as `eyes` or `mouth` exist.
Projects can define any tracks required by their characters, including
`eyebrows`, `tears`, `accessories`, or `fx`.

## FaceSpriteLibrary

`FaceSpriteLibrary` contains a list of sprite tracks.

Each sprite track contains:

- Unique generated Track key
- Editable Track name
- Atlas texture
- Grid size
- Sprite entries

Each sprite entry contains a generated key, an editable name, and an atlas
coordinate. Runtime lookups are dictionary-backed and deterministic.

## FaceState

`FaceState` represents the persistent facial appearance and contains a list of
Track States.

Each Track State contains:

- A Track key selected from the assigned library
- A Default Frame key selected from the frame mappings
- Frame mappings with generated keys and editable names

Each mapping connects a generated Frame key to a generated Sprite key in the
matching library track. The Inspector displays names instead of these keys.

The Default Frame key explicitly identifies the persistent frame. It resolves
through the frame mappings and is independent from list ordering. All mappings
remain available to `FromState` animations.

States do not perform timing or playback.

## FaceAnimation

`FaceAnimation` contains a dynamic list of Animation Tracks.

Each Animation Track contains:

- A Track key selected from its source
- Enabled state
- Frame source
- Timed frames

`FromState` frames resolve generated Frame keys through the active `FaceState`.
`CustomLibrary` frames resolve generated Sprite keys through the animation's
`FaceSpriteLibrary`.

Animations override only the Track keys they contain. When an animation ends,
the next update naturally restores the active state's base frame.

Playback modes:

- Sequential
- Loop
- Interval
- Random

## FaceController

`FaceController` owns:

- Registered states
- Registered animations
- Active state
- Active animation players
- Track bindings

Runtime order:

1. Resolve each state's base track frame.
2. Resolve active animation overrides.
3. Apply the final frame for each Track key to its binding.

Starting an animation stops existing animation playback only for matching
Track keys. There is no restore stack, animator graph, blend tree, or state
graph.

## Track Bindings

A Track Binding contains:

- Track key selected from a registered state library
- `Renderer`
- Material Index

Bindings support both `MeshRenderer` and `SkinnedMeshRenderer` through Unity's
common `Renderer` API.

Atlas properties are applied with:

```csharp
renderer.SetPropertyBlock(block, materialIndex);
```

This supports:

- Separate renderers with material index `0`
- Multiple tracks on one shared renderer
- Bone-driven meshes using `SkinnedMeshRenderer`

## Material Properties

Face shaders must expose:

```text
_MainTex
_Tiling
_Offset
```

The controller calculates:

```text
Tiling X = 1 / Columns
Tiling Y = 1 / Rows

Offset X = Column / Columns
Offset Y = (Rows - 1 - Row) / Rows
```

Material instances must not be created at runtime. Updates use a cached
`MaterialPropertyBlock` per binding.

## Validation

Validation reports:

- Empty or duplicate Track keys
- Missing atlas textures
- Invalid grid sizes
- Sprite coordinates outside the grid
- Empty or duplicate Sprite keys
- Missing Frame keys
- Empty Default Frame keys
- Default Frame keys missing from their Track State mappings
- Missing Sprite keys
- Missing library tracks
- Missing renderers
- Invalid material indices
- Invalid animation durations

Missing data is not guessed and does not silently fall back to another track.

## Transparency and Render Order

Transparent facial materials may be sorted differently from physical mesh
depth. Explicit material Render Queue values can provide stable ordering:

```text
Eyes Material  = 3000
Mouth Material = 3010
```

The correct order depends on the character. Render Queue ordering is often
preferable to moving meshes solely to influence transparent sorting.

## Shader Support

Available shader implementations:

- URP: `Samples~/UniversalRenderPipeline/FaceAtlasShader.shadergraph`
- Built-in Render Pipeline: `Shaders/FaceAtlasBuiltIn.shader`

Built-in projects should use `Face/Atlas Built-In` instead of converting the
project to URP.
